# 중요 미결정 사항

이 문서는 구현 결과를 크게 바꿀 수 있는 질문을 추적한다. 결정하면 상태를 `결정`으로 바꾸고 날짜, 선택, 근거를 적은 뒤 요구사항/도메인/아키텍처에도 반영한다.

## 구현 전 우선 결정

### OQ-01 인증 방식과 운영자 역할

- 상태: 결정
- 결정(2026-08-20): 서비스 DB의 로컬 계정과 Spring Security 세션 인증을 사용한다. 초기 실제 발급 역할은 `ADMIN` 하나다.
- 확장: 계정과 역할은 다대다로 모델링한다. 향후 `MEMBER`, `SITE_ADMIN`, `GROUP_LEADER`, `STAFF`를 추가할 수 있으며 한 계정에 여러 역할을 부여할 수 있다.
- 후속 결정: 초기 관리자 발급과 비밀번호 재설정의 운영 절차는 구현 시 문서화한다. 운영 환경의 인증 생략은 허용하지 않는다.
- 추가 결정(2026-08-21): 로그인 화면의 게스트 진입은 `VIEWER` 세션을 발급한다. 게스트는 데이터 조회만 할 수 있고 등록·수정·상태 변경·출석·쿠폰·QR 처리 API는 서버에서 거부한다. `VIEWER`는 모임 내 회원 직책과 무관한 애플리케이션 접근 권한이다.

### OQ-02 회원 생명주기와 재가입

- 상태: 결정
- 결정(2026-08-20): `Member.id`는 화면에 노출하지 않는 내부 UUID다. 재가입은 관리자가 후보를 확인한 뒤 기존 Member를 재활성화하거나 새 Member로 등록한다.
- 불변조건: 이름/외부 닉네임만으로 자동 병합하지 않는다. 기존 Member 재활성화 시 과거 출석과 쿠폰 이력은 같은 내부 ID에 그대로 보존된다.

### OQ-03 활동 제외 기간

- 상태: 일부 결정
- 결정 시점: Member migration 작성 전
- 결정(2026-08-19): `MemberActivityExclusion(startDate, endDate, reason)`로 관리하며 `endDate = null`인 무기한 활동 중단을 허용한다. 복귀 시 종료일을 기록하고 기간 중첩은 금지한다.
- 남은 질문: 월 일부만 제외된 회원을 활동률에서 어떻게 계산하는가?
- 제안: 월 인정 기준은 별도 통계 정책으로 두고 Phase 4 전에 예시 데이터로 확정한다.

### OQ-04 출석부 단위

- 상태: 일부 결정
- 결정(2026-08-20): `Gathering`을 별도 엔티티로 두고 `heldOn`의 unique 제약을 두지 않아 하루 여러 모임을 허용한다. MVP에는 선택적인 제목·시작 시각·장소와 `DRAFT | OPEN | CLOSED | CANCELLED` 상태를 둔다.
- 결정(2026-08-24): 정모는 `CLASS`(수업) 또는 `EVENT`(행사)다. 행사는 시작일과 종료일을 필수로 기록하며 종료일은 시작일보다 앞설 수 없다. 달력에는 행사 기간 전체를 표시하고, 출석은 시작일 정모에 기록한다.
- 남은 질문: 제목·시작 시각·장소를 실제 운영에서 필수로 할지, 마감 후 취소/재개를 허용할지.

- 결정(2026-08-21): 모임 취소에는 사유를 필수로 기록한다. 취소된 모임은 기본 목록·캘린더에서 제외하고, 취소 이력 화면에서 최근 취소 순으로 페이지 처리해 조회한다.

### OQ-05 출석 기록 정정

- 상태: 일부 결정
- 결정(2026-08-20): 출석은 물리 삭제하지 않고 `RECORDED | CANCELLED` 상태와 취소 시각·사유를 기록한다. `(gathering_id, member_id)`는 취소 이력까지 포함해 하나만 유지한다.
- 남은 질문: 쿠폰 사용 출석을 취소할 때 쿠폰 잔액을 자동 복원할지. Coupon Phase에서 한 트랜잭션 유스케이스로 결정한다.

### OQ-06 월간 통계의 대상 회원

- 상태: 미결정
- 현재 구현: `docs/statistics-policy.md`의 `draft-v1`은 가입일~탈퇴일이 대상 월과 하루라도 겹치면 분모에 포함한다. 이는 운영진 확정 전의 조회용 초안이다.
- 결정 시점: Phase 4 시작 전
- 질문: 월초/월말/월중 어느 시점의 회원을 분모로 보는가? 월중 가입·탈퇴자는 어떻게 하는가?
- 제안: 임의의 월말 스냅샷보다 가입일/탈퇴일과 월의 교집합으로 대상자를 산정하고 상세 대상을 함께 표시한다. 최종 업무 규칙은 운영진이 예시 데이터로 승인해야 한다.

### OQ-07 활동률 공식

- 상태: 미결정
- 현재 구현: `draft-v1`은 출석 회원과 해당 월 활동 중단 기간이 겹치는 회원의 합집합을 분자로 계산한다. 이는 운영진 확정 전의 조회용 초안이다.
- 결정 시점: Phase 4 시작 전
- 질문: `(출석자 + 활동 제외자) / 대상자`에서 두 집합 중복을 어떻게 처리하며, 일부 기간 제외도 한 명으로 인정하는가?
- 제안: 합집합으로 중복을 제거한다. 정책 버전과 예시(가입, 탈퇴, 월 일부 휴식, 출석 후 휴식)를 먼저 표로 확정한다.

### OQ-08 출석왕 동률과 자격

- 상태: 결정
- 결정(2026-08-20): 1명이거나 공동 1등이 2명이면 각 2회 무료 쿠폰을 발급한다. 공동 1등이 3명 이상이면 각 1회 무료 쿠폰을 발급한다. 무료/쿠폰 출석은 집계에서 제외한다.
- 결정: 보상 횟수는 버전이 있는 `ChampionRewardPolicy`로 관리하고, Award에는 적용 정책 버전과 실제 발급 횟수를 스냅샷으로 남긴다. 정책 변경은 이후 대상 월에만 적용하며, 기존 발급 결과를 다시 계산하거나 중복 발급하지 않는다.
- 결정(2026-08-20, 갱신 2026-08-24): 해당 월에 `NORMAL` 출석을 한 일반 회원(`MEMBER`) 중 최다 출석자가 수상한다. 운영진(`STAFF`)과 모임장(`LEADER`)은 집계에서 제외한다. 최소 출석 횟수와 수상 시점의 탈퇴 상태에는 별도 제한을 두지 않는다. 자격을 갖춘 일반 회원의 `NORMAL` 출석자가 없는 달은 수상자 없음이다.

### OQ-09 출석왕 확정과 재계산

- 결정 시점: Phase 4 시작 전

- 제안: 계산 미리보기와 관리자 확정을 분리하고 확정 결과에 정책 버전/횟수를 저장한다. 확정 후 정정은 자동 회수하지 않고 별도 보정 절차를 둔다.

### OQ-10 쿠폰 단위와 사용 모델

- 상태: 미결정
- 결정 시점: Coupon migration 작성 전
- 질문: 2회 보상을 2장의 1회권으로 발급할지, 2회 잔액 쿠폰 한 장으로 발급할지? 부분 사용/양도/사용 취소를 허용하는가?

### OQ-11 쿠폰 만료와 삭제

- 상태: 미결정
- 결정 시점: Phase 5 시작 전
- 질문: 만료를 날짜로 계산할지 상태로 저장할지, 미사용 오발급의 물리 삭제를 허용할지?
- 제안: 만료는 날짜에서 계산하고 오발급은 `VOIDED` 처리한다. 물리 삭제는 운영 데이터에서 허용하지 않는다.

### OQ-12 QR 보안과 공개 범위

- 상태: 결정
- 결정(2026-08-21): QR 발급·검증·사용은 인증된 `ADMIN`만 수행한다. QR에는 32바이트 난수 토큰만 넣고 DB에는 SHA-256 해시만 보관한다.
- 결정: 새 QR 발급은 기존 토큰을 교체하며, 사용자는 발급 전 이를 확인한다. 스캔 후 서버 검증과 운영자 사용 확인을 거친 뒤에만 출석과 쿠폰 사용을 한 트랜잭션으로 기록한다.
- 범위: 회원용 공개 QR 페이지나 QR 공유 정책은 MVP에 포함하지 않는다.

### OQ-18 회원 직책과 로그인 권한

- 상태: 결정
- 결정(2026-08-21): `Member.memberRole`은 모임 내 직책으로 `MEMBER`(회원), `STAFF`(운영진), `LEADER`(모임장)를 사용한다. 신규·기존 회원의 기본값은 `MEMBER`다.
- 불변조건: 회원 직책은 `UserAccount`의 로그인·인가 권한과 분리한다. 운영진 또는 모임장으로 지정해도 관리자 계정이 자동 생성되거나 로그인 권한이 부여되지 않는다.
- 이유: 현재는 운영진 전용 관리자 앱이며, 회원용 로그인과 세분화된 권한 정책은 범위 밖이다. 직책 표시와 출석·통계 이력은 먼저 안정적으로 관리한다.

### OQ-13 외부 명부 스크린샷 동기화

- 상태: 미결정

- 제안: OCR 결과를 즉시 반영하지 않고 현재 명부와 비교한 가입/탈퇴 후보를 운영자가 승인하게 한다. 외부 API 제공 여부도 먼저 확인한다.

### OQ-14 Markdown 정책

- 상태: MVP 결정
- 결정: `react-markdown`과 `remark-gfm`으로 CommonMark/GFM 요소를 렌더링한다. raw HTML, 임의 스크립트, 외부 이미지/첨부파일, Mermaid는 MVP에서 허용하지 않는다.
- 이유: 요구된 제목, 목록, 강조, 표, 체크박스, 코드 블록을 충족하면서 raw HTML 렌더링 경로를 만들지 않는다.

### OQ-16 배포, 백업, 개인정보

- 상태: 일부 결정
- 결정(2026-08-21, 갱신 2026-08-25): 프론트는 Cloudflare Workers Static Assets, 백엔드는 Render Free Web Service, DB는 기존 Neon PostgreSQL을 사용한다. URL·DB 연결·초기 관리자·CORS origin은 플랫폼 환경변수/secret으로만 관리한다.
- 추가 결정(2026-08-25): Cloudflare Worker가 `/api/*`를 Render로 프록시한다. 정적 Asset Worker는 POST를 처리하지 않아 405를 반환할 수 있으므로, `assets.run_worker_first`로 `/api/*`를 명시적으로 Worker에 전달한다. Render URL은 Worker의 서버 측 `API_ORIGIN`으로만 관리하며, 브라우저 세션은 first-party 쿠키로 유지한다. 이는 iPhone Safari의 제3자 쿠키 차단을 피하기 위한 결정이다.
- 남은 질문: 운영 도메인, Neon 백업 보존 기간과 복구 리허설, 개인정보 보존·삭제 요청 절차.
- 주의: Render Free 인스턴스의 제한은 운영 전 점검한다. 추후 자체 도메인을 도입하면 프론트/API를 같은 등록 도메인의 하위 도메인으로 구성할 수 있다.

### OQ-17 오픈소스 라이브러리 선정

- 상태: 미결정
- 결정 시점: 각 의존성 도입 직전
- 질문: QR 생성/스캔, Markdown 렌더링/편집, 보안 sanitization 라이브러리는 무엇인가?
- 평가 기준: OSI 계열 라이선스와 상업적 무료 사용 가능성, 최근 유지보수, 보안 이력, 번들 크기, 브라우저 지원, 접근성, 대체 가능성. 선택 결과와 라이선스를 의존성 결정 기록에 남긴다.
